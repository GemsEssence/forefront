# Renewal Tickets reference Customer + Product, not a Lead; Subscription is a new, separate entity

A renewal Ticket names a Customer and a Product (`Ticket belongs_to :product, optional: true`), not the Lead that originally sold it — deliberately, even though the obvious alternative (`Ticket belongs_to :lead`) would have been simpler to build. Ticket already has no `lead_id` at all, despite CONTEXT.md describing it as "optionally connected to a Lead" since the very first domain-modeling session; that link was never implemented, and this decision replaces it rather than completing it. A `Forefront::Subscription` (Customer + Product + `expires_at`, one per won Lead, created automatically on win) is the actual join point renewal/reclaim logic reasons about, since a Customer can hold multiple Subscriptions across multiple Leads and only Customer+Product unambiguously identifies which one a given Ticket is about.

This also sets up the two ways a renewal Ticket can be created going forward: manually by staff (Customer + Product only, no Lead required), or later via an external API once Forefront supports being used as a plugin — neither needs a Lead in scope, so the Ticket model shouldn't require one either.
